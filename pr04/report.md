# ПР №4. Аудит событий: journalctl и auditd

## 1. journalctl — системный журнал

### Что зафиксировал журнал о команде sudo cat /etc/shadow

Пример строки из `journalctl _COMM=sudo` (команда выполнялась от posasun):
мая 14 12:30:51 EgorEblan2006 sudo[3139]: posasun : TTY=pts/0 ; PWD=/home/posasun ; USER=root ; COMMAND=/usr/bin/cat /etc/shadow

**Разбор полей:**
- Дата/время: `мая 14 12:30:51`
- Хост: `EgorEblan2006`
- Процесс: `sudo[3139]`
- Пользователь: `posasun`
- Терминал: `TTY=pts/0`
- Рабочая директория: `PWD=/home/posasun`
- Целевой пользователь: `USER=root`
- Команда: `COMMAND=/usr/bin/cat /etc/shadow`

### Ошибки в системе с момента последней загрузки

Команда `journalctl -p err -b` не вывела ни одной записи, что означает отсутствие критических ошибок.

### Статистика входов

- Успешных входов через SSH: `0` (на виртуальной машине входы не выполнялись)
- Неудачных попыток входа: `0`

## 2. auditd — настройка правил

### Применённые правила (вывод auditctl -l)
-w /etc/passwd -p rwa -k auth-files
-w /etc/shadow -p rwa -k auth-files
-w /etc/group -p rwa -k auth-files
-w /etc/sudoers -p rwa -k priv-files
-w /etc/sudoers.d -p rwa -k priv-files
-w /etc/ssh/sshd_config -p rwa -k ssh-config
-a always,exit -F arch=b64 -S open,openat -F success=0 -F key=access-denied
-a always,exit -F arch=b64 -S unlink,unlinkat -F key=file-delete
-a always,exit -F arch=b64 -S execve -F euid=0 -F auid!=0 -F auid!=-1 -F key=priv-exec

### Разбор одной записи SYSCALL

Рассмотрим запись для успешного чтения `/etc/passwd` пользователем bob:
type=SYSCALL msg=audit(14.05.2026 12:39:22.706:753) : arch=x86_64 syscall=openat success=yes exit=3 a0=AT_FDCWD a1=0x7ffda54ad82c a2=O_RDONLY a3=0x0 items=1 ppid=3254 pid=3259 auid=posasun uid=bob gid=bob euid=bob suid=bob fsuid=bob egid=bob sgid=bob fsgid=bob tty=pts0 ses=3 comm=cat exe=/usr/bin/cat subj=unconfined key=auth-files

| Поле | Значение | Что означает |
|------|----------|---------------|
| auid | posasun | Аутентифицированный пользователь (исходная сессия) |
| uid  | bob      | Реальный ID пользователя во время вызова |
| euid | bob      | Эффективный ID (используется для проверки прав) |
| comm | cat      | Имя команды (без пути) |
| exe  | /usr/bin/cat | Полный путь к исполняемому файлу |
| key  | auth-files | Метка правила, сработавшего для этого события |

## 3. Расследование инцидента

### Хронология действий bob (на основе ausearch)

| Время | Действие | Результат | Ключ правила |
|-------|----------|-----------|---------------|
| 12:39:09 | `cat /etc/shadow` | Отказ (EACCES) | auth-files |
| 12:39:15 | `ls /root` | Отказ (EACCES) | access-denied |
| 12:39:22 | `cat /etc/passwd` | Успех | auth-files |
| 12:39:54 | `cat /etc/sudoers` | Отказ (EACCES) | priv-files |

Дополнительно: создание файла `/tmp/totally-not-malware.sh` (команда `touch`) не было зафиксировано правилом `file-delete`, так как это создание, а не удаление. Для отслеживания создания можно добавить правило `-S creat -S open` с флагами создания.

### Как auditd помог расследованию

- Обнаружил все попытки несанкционированного доступа к защищённым файлам (`/etc/shadow`, `/etc/sudoers`).
- Позволил отличить разрешённые операции (чтение `/etc/passwd`) от запрещённых.
- Зафиксировал оригинального пользователя (`auid=posasun`) даже после переключения на `bob`, что важно для выявления реального нарушителя.
- Предоставил детальную информацию о каждом системном вызове (аргументы, флаги, код ошибки).

### Чем auditd лучше journalctl для задач аудита безопасности

| Характеристика | auditd | journalctl |
|----------------|--------|-------------|
| Уровень работы | Ядро (системные вызовы) | Пользовательское пространство (логи служб) |
| Защита логов | Аппендикс-файлы, только root | Может быть изменён администратором |
| Детализация | Параметры syscall, uid, euid, auid, успех/ошибка | Текстовые сообщения приложений |
| Обход | Требует прав root и модификации аудита | Приложение может не писать логи |
| Поиск | ausearch с ключами, фильтрами | journalctl с фильтрами, но менее детальный |

## 5. Контрольные вопросы (письменные ответы)

1. **Чем принципиально отличается auditd от journald? Почему нельзя обойтись только journald?**  
   auditd работает на уровне ядра и фиксирует системные вызовы, журнал невозможно обойти привилегированным процессом. journald собирает текстовые логи приложений, которые могут быть не написаны или подделаны. Для детального аудита безопасности (фиксация каждого системного вызова, параметров и auid) необходим auditd.

2. **Что такое auid и почему оно важнее uid при расследовании инцидентов с sudo?**  
   auid (audit user ID) — неизменяемый идентификатор пользователя, который выполнил вход в систему. При `sudo` или `su` uid меняется на целевого пользователя, но auid остаётся исходным. Это позволяет установить реального нарушителя, даже если он переключился на другого пользователя.

3. **Что означает флаг -k в правиле auditd? Для чего он используется?**  
   `-k` задаёт ключ (key) — произвольную метку, которой помечаются все события, сработавшие по этому правилу. Ключ используется для поиска событий через `ausearch -k ключ`, что упрощает анализ.

4. **Чем -w (watch) отличается от -a always,exit в правилах auditd? Когда использовать каждый?**  
   - `-w` — наблюдение за конкретным файлом или директорией. Удобно для мониторинга доступа к важным файлам.
   - `-a always,exit` — добавление правила на системный вызов (например, `open`, `unlink`) с возможными фильтрами (-F). Используется для глобального мониторинга операций без привязки к конкретному файлу (например, все неудачные открытия).

5. **Злоумышленник удалил файл /var/log/audit/audit.log. Как это помогает ему скрыть следы и как от этого защититься?**  
   Удаление логов затрудняет расследование, но само удаление может быть зафиксировано в логах, если настроено правило на удаление файлов (`-S unlink`). Защита: размещение логов на отдельном защищённом сервере (syslog/rsyslog), настройка правил на удаление, использование режима `append-only` или ограничение прав на удаление.

6. **Что нужно сделать чтобы правила auditd сохранились после перезагрузки?**  
   Поместить правила в файл в `/etc/audit/rules.d/` с расширением `.rules` (например, `security-course.rules`) и выполнить `sudo augenrules --load`. Затем включить службу `auditd` (`systemctl enable auditd`).
