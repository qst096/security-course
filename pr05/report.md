## 2. Шифрование

Создан файл `secrets.txt` с содержимым:
DB_PASSWORD=super_secret_password_123
API_KEY=sk-abc123def456
ADMIN_TOKEN=eyJhbGciOiJIUzI1NiJ9.test

Зашифрован командой:
gpg --encrypt --armor --recipient papirus.skeletov@mail.ru pr05/files/secrets.txt

Получен файл `secrets.txt.asc` (первые строки):
-----BEGIN PGP MESSAGE-----
hQIMA8+Y6Mfaf0YdAQ/+LbA1vHA17r+S177uyo9GjHpy3NrfcFS5iVH2xvFlWP0y
3Hiafn1coLqVHd+hSgyG1t/LqpRU8ma4icCc4p9D+aXcANIGJlb5Tg219V4slvWI
...

Из зашифрованного файла прочитать исходные данные невозможно.

Расшифровка выполнена:
gpg --decrypt pr05/files/secrets.txt.asc

Вывод:
DB_PASSWORD=super_secret_password_123
API_KEY=sk-abc123def456
ADMIN_TOKEN=eyJhbGciOiJIUzI1NiJ9.test

При вводе неверного пароля расшифровка не выполняется (ошибка `Bad passphrase`).

## 3. Цифровая подпись

Создан файл `agreement.txt`:
Я, posasun, подтверждаю что прочитал политику ИБ компании.
Дата: Вт 12 мая 2026 12:16:26 +05

Создана отдельная подпись:
gpg --armor --detach-sign pr05/files/agreement.txt

Проверка подписи до изменения файла:
gpg: Подпись сделана Вт 12 мая 2026 12:18:15 +05
gpg: ключом RSA с идентификатором A4D9595BA147AB20F10F933A270183134328E518
gpg: Действительная подпись пользователя "posasun papirus.skeletov@mail.ru" [абсолютное]

После добавления в файл строки «Дополнение: ничё не разрешаю...» проверка подписи выдала:
gpg: ПЛОХАЯ подпись пользователя "posasun papirus.skeletov@mail.ru" [абсолютное]

Подпись перестала быть действительной, потому что файл был изменён.  
`gpg --verify` проверяет, что файл не был изменён после подписания, и что подпись принадлежит указанному ключу.

## 5. rm vs shred

### Эксперимент с `rm`
- Создан файл `/tmp/secret-data.txt`, inode = 1046567.
- После `rm` файл не виден в файловой системе.
- Данные на диске могли остаться (восстановление возможно до перезаписи блоков).

### Эксперимент с `shred`
- Создан файл `/tmp/to-be-shredded.txt`, inode = 1046567.
- Команда `shred -v -n 3 -z -u` выполнила:
  - проход 1/4 (random)
  - проход 2/4 (random)
  - проход 3/4 (random)
  - проход 4/4 (000000)
  - удаление с многократным переименованием.
- После `shred` восстановить данные невозможно, так как содержимое перезаписано.

### Сравнение

| Операция | Что происходит с данными на диске | Можно восстановить? |
|----------|-----------------------------------|---------------------|
| rm | Удаляется только запись в inode, блоки данных остаются | Да (до перезаписи) |
| shred | Блоки перезаписываются случайными данными (3 раза) + нулями | Нет |

### Сценарий для затирания свободного места

При передаче диска другому лицу или продаже компьютера необходимо затереть свободное место, чтобы удалённые ранее файлы нельзя было восстановить. Для SSD `shred` неэффективен из-за выравнивания износа; рекомендуется использовать `blkdiscard` или утилиты с поддержкой TRIM.
